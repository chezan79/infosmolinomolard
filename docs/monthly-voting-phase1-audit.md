# Collaborateur du mois — Phase 1 voting-system audit

**Scope:** source-code and test inspection for the September 2026 election; audit only. The description that the election is live and has received a real vote is **not independently verified**. This document describes the implemented system, not a certification of deployed behavior. `docs/employee-of-the-month-architecture.md` contains both an implemented-operations summary and older *proposed* designs; the executable files cited below govern this audit.

## 1. Architecture and trust boundaries

`server.js:31-85,128-131,648-666` initializes Firebase Admin, the directory and election runtimes, mounts the election API before the global JSON parser, serves the protected Administration page and public voting page, and starts the directory before listening. No durable election fallback exists when Firebase/configuration is missing. `election-engine/index.js:36-48` requires a site ID and explicit `development` or `production` election namespace. `production-config.js:61-111` requires the production namespace, Molard site and Europe/Zurich timezone when `NODE_ENV=production`; this is a startup policy, **not proof of which project or environment is currently serving real voters**.

The directory is a server-read Google Sheet → validated, last-known-good Firestore snapshot → immutable monthly election voter/candidate snapshot. `employee-directory/google-sheets-source.js:3-42` requests the server-configured sheet with read-only scope and size/time limits; `employee-directory/contract.js:3-19,85-210,230-334` normalizes IDs, site, flags, departments, verifiers and photos, rejecting invalid/duplicate data. `employee-directory/service.js:19-99,105-110` loads a validated stored snapshot and periodically replaces it only after validation. An existing election is **not** changed by later directory refreshes (`election-engine/firestore-store.js:26-60`). The browser communicates with same-origin Express APIs, not Firestore. Firebase Admin bypasses Firestore browser rules, making server authorization and service-account access critical.

`election-engine/contract.js:22-66` derives the local `YYYY-MM` and persists UTC open/close instants: inclusive midnight on the 25th, exclusive midnight on the first of the next month in the configured IANA timezone. States are computed, not persisted: `UPCOMING`, `OPEN`, `CLOSED_PENDING_RESULTS`; a finalized-result document does not change the state response to `RESULTS_FINAL`.

## 3. Actual HTTP endpoints and callers

`election-engine/index.js:49-73` mounts five public routes, all with `Cache-Control: no-store`; POST bodies have a 16 KiB JSON limit. `GET /api/v1/public/election` returns month, computed state, dates, server time, categories and **aggregate** eligible/submitted counts. `POST /api/v1/public/election/verify-code` receives a personal code, rate-limits attempts and returns a short-lived Bearer authorization on success. `GET /api/v1/public/election/candidates` and `GET /api/v1/public/election/participation` require that grant; the latter answers only for its holder. `POST /api/v1/public/election/ballots` requires the grant and both choices and comments; successful responses use HTTP 201. The frontend (`collaborateur-du-mois.js:75-128,140-200`) keeps the grant and draft ballot in page memory, checks participation, presents searchable candidate cards, reviews the choices/comments and submits once. It hides results, but client hiding is not an authorization boundary.

`server.js:66-105` protects `GET /administration` and `/administration.html` with session middleware and exposes unauthenticated *operational readiness* (`GET /api/v1/operations/election-readiness` and `/readyz`), neither of which is a safe live-election health query. `employee-directory/index.js:98-169` mounts management session creation/deletion, directory status/refresh and photo routes; no election management, result, individual participation-list or dashboard API is mounted. `ElectionService.finalize(monthKey)` is internal only (`election-engine/service.js:112-116`). In particular, merely calling the public election/status/verification APIs for an audit is **not read-only**: each calls `current()` and can create the monthly election (`service.js:20-26`, `firestore-store.js:26-57`); verification additionally writes throttles/grants/audit records.

All election paths are under `electionSites/{siteId}/dataEnvironments/{development|production}` (`election-engine/firestore-store.js:10-24`). `{siteId}` and namespace are server configuration, not client-supplied.

## 5. Successful vote and failure/atomicity sequence

1. Public status computes the month and ensures the immutable election exists. Code verification (`election-engine/service.js:40-65`) requires `OPEN`, validates input length, derives a peppered HMAC verifier, applies transactional network/site-month/credential rate limits, compares against snapshotted eligible voters, creates a server-side grant and writes an audit event. It returns only the opaque token and expiry, not an identity. Verification writes are **not** one transaction: if audit fails after grant creation, the caller may receive an error even though the grant exists.
2. With the Bearer grant, the voter checks participation and retrieves candidates (self omitted). `validateBallot` (`election-engine/contract.js:68-85`) requires exactly `choices` and `comments`, exactly `CUISINE` and `SERVICE` in each, valid candidate-ID syntax, and each trimmed comment 10–1000 characters. The HTTP handler maps recognized errors to 400/401/409/429 and unexpected or unlisted election errors to 503 (`election-engine/index.js:49-58`).
3. `ElectionService.submit` validates shape **before** authorization, then authorizes the current month with consumed-grant replay allowed (`service.js:93-104`). `FirestoreElectionStore.submit` allocates a random ballot reference before the transaction, then transactionally reads the election and grant, checks grant scope, reads deterministic participation, handles an already-consumed same-grant replay, rechecks expiry and **server time** for `OPEN`, checks snapshotted voter and both category-matched non-self candidates, and rejects existing participation (`firestore-store.js:104-130`).
4. The same Firestore transaction creates participation and the anonymous ballot and marks the grant consumed (`firestore-store.js:131-135`). If validation, Firestore reads or commit fail, none of these three writes should commit; after a successful commit, a separate best-effort coarse audit write cannot undo the ballot (`service.js:97-103`). HTTP/network failure after commit remains ambiguous to the browser: retrying the **same** grant and valid ballot within the current month returns `SUBMITTED` with `replayed: true`; a **different** grant for the same voter gets `ALREADY_VOTED`. A consumed-grant replay does not compare the retried ballot and can return success after the close *while the same month is current*; it does not write a second ballot. On calendar rollover, authorization resolves a different month and the old grant fails.

No code here proves the state of a deployed Firestore database or that write timing at the exact close boundary cannot drift between transaction callback time and commit. The emulator test exercises the real repository's simultaneous-write shape, not a production race.

## 6. Participation versus ballot separation — **ANONYMITY SEPARATION: WARNING**

**Code-supported positive evidence:** the participation ID identifies the employee but its body has no choice/comment or ballot reference; the ballot has random ID and only choices/comments; the grant is consumed in the same transaction without being stored on the ballot (`firestore-store.js:104-135`). Neither public nor management routes return raw ballots or voter-linked choices. Browser Firestore reads are denied (`firestore.rules:5-18`). `test/election-engine.test.js:156-173` and `test/firestore-rules.emulator.js:59-94` assert ballot shape in test environments.

**Why WARNING, not an anonymity guarantee:** a privileged Firestore operator or service account may correlate near-simultaneous database writes/metadata, grants and identity, especially with few votes; free-text comments can themselves identify the author. Audit hour buckets are coarse but verification and submission patterns may still be informative. No demonstrated retention, access logging/redaction policy, comment moderation or protection against privileged exports/backups is implemented. Never join participation to ballots, attach exact timestamps to ballots, or expose raw comments in an open-election dashboard.

## 7. Duplicate prevention, concurrency and retries — **DUPLICATE VOTE PROTECTION: PASS**

**Core invariant supported by code:** one participation document ID per employee per month and a transactional `create` plus ballot `create` plus grant consumption (`firestore-store.js:117-135`). Concurrent attempts using different grants observe the same participation document; Firestore transaction conflict/preconditions permit at most one successful commit. A same-grant retransmission after commit returns idempotent success without creating a new ballot; a different grant sees `ALREADY_VOTED`. Month-scoped paths allow a later month's vote. The unit double tests basic replay/concurrency (`test/election-engine.test.js:156-191`) and the emulator tests two simultaneous grants against actual Firestore transaction semantics (`test/firestore-rules.emulator.js:59-94`).

**Qualification:** the emulator does not test high-contention production retries, transient transaction failures or close-boundary commits. A consumed grant can acknowledge any structurally valid retry body without proving it matches the original, though no new vote is recorded. An expired *unconsumed* grant cannot submit; a consumed one remains replay-acknowledgeable in its current month. Operational tests should preserve the invariant without submitting a live vote.

## 8. Administration authorization at UI, route, API and rules layers

The Administration menu currently links to photo management only (`private-pages/administration.html:17-25`); there is **no voting-monitor UI**. The client login exchanges a Firebase ID token for an eight-hour, `HttpOnly`, `Secure`, `SameSite=Strict` session cookie (`employee-directory/index.js:98-126`). The authorized identity is an **exact configured UID plus matching site claim**, not a generic `manager` role (`employee-directory/auth.js:21-58`); this is the present Andrea-only mechanism *if* the configured UID is Andrea's, which this audit cannot verify. A voter grant has no management privileges. `/administration` and its `.html` alias check the session before sending the private file (`server.js:66-73`, `auth.js:75-90`); public static serving excludes that file (`public-files.js:16-28`). Existing management status/photo APIs separately verify the session; mutating management routes generally require same-origin checks (`employee-directory/index.js:132-168`). The Administration logout JavaScript sends DELETE without an `Origin` header explicitly; ordinary same-origin browsers supply Origin for this request, but the server rejects it if absent (`administration.js:1-10`, `auth.js:61-73`).

No protected election monitoring API exists today. A new route must verify the session **server-side on every request**, constrain month/site server-side, return only allowed aggregate fields, and avoid exposing full directory status, raw ballots or results while open. `firestore.rules:5-18` denies browser reads/writes to both entire election tree and directory snapshots for any browser identity; Admin SDK bypasses those rules. Tests cover exact UID/site and directory status (`test/employee-directory.test.js:308-349,399-427`) and rules rejection (`test/firestore-rules.emulator.js:46-57`); they do **not** prove a future monitoring API's access controls.

## 9. Result sealing, finalization and ties — **RESULT SEALING: PASS**

`election-engine/firestore-store.js:144-180` rejects `tally()` before the persisted close instant, reads ballots only after close, and creates the single `resultInternals/final` document transactionally after rechecking closure; subsequent calls return that same stored result. `ElectionService.finalize` only accepts a month-shaped argument and calls this internal repository path (`service.js:106-116`); it is **not mounted as a public or manager HTTP route**. Winner logic includes every candidate sharing a positive maximum, sorted by ID, and none at zero (`contract.js:96-103`); tests cover rejection while open and a tie primitive (`test/election-engine.test.js:193-210,283-297`). No candidate standings, result document or ballot-reading API is exposed while open, and browser rules deny direct reads.

**Boundary of PASS:** this is sealing against current application/browser interfaces, not a restriction on privileged Admin SDK/database operators. No automatic close/finalize scheduler, result-publishing policy, audited manager confirmation or consistency reconciliation is implemented. `finalize` first scans ballots outside the result-creation transaction; it is safe against ordinary voter submissions after close under the current time gate, but not proven against privileged out-of-band ballot modifications. The existing-result fast path does not re-evaluate lifecycle; it returns only to an internal caller today. `publicState()` still reports `CLOSED_PENDING_RESULTS` even after a result is stored.

## 11. Dashboard-safe sources and latest participation timestamp

For the open election, a new authenticated API could return the election's scalar month/window/state and `eligibleVoterCount`, a server-side count of `participation` documents and the ratio; it may use directory service's *redacted aggregate* status (`employee-directory/service.js:124-163`) after scoping and minimization. The existing unauthenticated public election endpoint exposes eligible/submitted aggregate counts, but it can initialize an election and is **not** a read-only dashboard source. A protected backend should use direct existence/read/count paths that never invoke `current()`/`ensureElection()`, explicitly distinguish “not created” from “zero votes,” and use `Cache-Control: no-store`. For integrity checks, compare aggregate participation and ballot counts inside the server only, without returning raw docs.

**Latest participation timestamp: unavailable from the application schema.** Participation records contain no timestamp; ballots contain none. Firestore's per-document metadata could reveal exact timing but would require reading identity-bearing participation documents and is unsuitable for this dashboard. Do not fabricate a last-vote time from audit hour buckets (they are not participation records, may be missing after committed votes and mix outcomes) or from ballot metadata. If product requires this metric, design a privacy-reviewed coarse aggregate, updated safely without a voter/ballot join; do not retroactively claim it for September.

After close, the existing `resultInternals/final` is suitable only as a protected source for a separately approved post-close results feature, never as an open-election dashboard payload. Do not expose its candidate counts, winners, comments or raw ballot content in this monitoring dashboard.

## 12. Reusable components

Reuse `electionWindow`/`electionState` for server-derived calendar semantics, `FirestoreElectionStore`'s site/namespace path pattern (but **not** its creating `ensureElection` path for monitoring), the directory's validated snapshot and aggregate `getStatus()`, the existing Firebase Admin initialization, exact UID/site session authorization (`createAdministrationSessionAuthorization`), protected page/static-file pattern, and `no-store` response convention. The Administration menu/card styling is reusable. Build a dedicated **read-only** monitoring repository/service rather than calling `publicState()`, `verify()` or `finalize()`. Prefer Firestore aggregate count operations for counts over fetching participant documents; the current `participationCount()` scans the collection (`firestore-store.js:99-102`).

## 13. Security and privacy risks

**Highest priority:** no live identity/data verification; avoid pointing a future dashboard at Preview or a different Firebase project and reporting that as September production. Election snapshot embeds employee identifiers and verifier material in one server-only document; protect service-account access, exports and backups, and avoid accidentally serializing the document through a management route. Code verifiers are fast keyed HMACs, not a slow password hash (`employee-directory/contract.js:63-68`); actual personal-code entropy is unknown. Rate limits are durable and layered but have no demonstrated automatic cleanup; shared network caps and the site-wide cap could deny legitimate voters (`election-engine/service.js:40-51`, `firestore-store.js:67-79`). These issues need security/product decisions, not a live-data probe.

**Privacy/integrity:** free-text comments can self-identify; database metadata and privileged operators can correlate close writes; per-identity grants persist until cleanup. A reply lost after a successful ballot commit is recoverable by same-grant replay, but another grant reports `ALREADY_VOTED`. Verification auditing can fail after a grant write. The UI text promises that individual choices/results will not be displayed, so any future results/comment experience needs a clear policy rather than assuming permission. Existing public aggregate participation is visible during voting; suppress or delay it if small-group privacy policy requires it.

## 14. Blockers and required decisions before Phase 2 construction

1. **Confirm real target and access:** independently establish the deployed Firebase project/database, production site/namespace, intended September month and Andrea's UID/site claim via trusted operator configuration; do not use current Preview configuration as proof. No live September counts can be placed in a dashboard or report until this is established.
2. **Specify permitted outputs:** approve an Andrea-only, aggregate-only monitoring contract and small-group disclosure policy. Decide whether public aggregate participation should remain public. Exclude open candidate standings, raw ballots/comments, identity-bearing participation and exact per-vote times.
3. **Define non-creating read behavior:** implement protected, read-only month-scoped queries with explicit “missing election” and storage-error states and backend reconciliation of counts; do not use an endpoint that initializes election state. Bound queries, minimize returned fields and test production/development namespace isolation.
4. **Resolve timestamp request:** show “not available” unless a privacy-reviewed coarse aggregate is added for *future* submissions; do not infer September's last vote from document metadata.
5. **Decide post-close workflow separately:** manager approval, close/finalization, tie display and published results are not implemented here and belong to a separate authorized workflow; do not unblock this dashboard by invoking internal `finalize()` on live data.

These are implementation prerequisites for a trustworthy dashboard, not changes performed by this audit.

## 15. Recommended Phase 2 design and verdict

Add one Administration card and a server-rendered or same-origin client page guarded by `authorizeAdministrationPage`. Add a new `GET /api/v1/management/election-monitor?month=YYYY-MM` guarded on **every request** by `createAdministrationSessionAuthorization`; derive site and environment only from trusted server configuration, constrain the requested month, read scalar election metadata without creating it, and count participation/ballots using read-only aggregate operations. Return a small explicit response (`month`, computed window/state, eligible count, submitted count, optional internal consistency indicator, data-source status), with no identities or candidate-level data. Use no-store and test unauthenticated/wrong UID/wrong site, missing document, namespace isolation, zero-vote election, open-result secrecy and count failure. Display “latest participation: unavailable” unless an approved safe aggregate is designed later. Preserve the current Firestore deny-all browser boundary and never expose the Admin SDK to the client. Keep post-close result management separate from monitoring.
